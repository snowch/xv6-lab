ecall crosses into the kernel

Follow getpid from its C call through the RISC-V ecall instruction.

Compiler and kernel run locally.
Your source stays in this browser.

The C declaration does not explain how a user program reaches protected kernel code. xv6 supplies a small assembly stub: a short function that arranges a system-call request.

The real getpid stub below loads SYS_getpid, the call’s number, into a7, a CPU register: a small storage location used here to hold the call number. The RISC-V instruction ecall then causes the CPU to enter xv6’s trap handling code. A trap transfers control so the kernel can handle an event; here the event is a user system call.

xv6’s usertrap recognises this event and calls syscall. That dispatcher uses the number to select sys_getpid, the kernel function that implements this request. After the kernel returns to user mode, the stub’s ret returns to the C caller.

getpid → ecall → usertrap → syscall → sys_getpid

C reminder: function declarations

A declaration tells the compiler a function’s name, parameter types and result type. void inside the parameter list means no arguments. The declaration describes how to call the function; its implementation can live elsewhere.

int getpid(void);  // no arguments; returns an int

What this shows

        
A C system-call name hides a real transition into the kernel. ecall initiates that transition; it does not itself choose or implement getpid.

        

          A question to carry forward
          
What tells the kernel which service the program requested: ecall alone, or the call number in a7?
