A returned value is not the stored value

Change the system-call answer while leaving the process record unchanged.

Compiler and kernel run locally.
Your source stays in this browser.

The handler currently returns the value stored in myproc()->pid. A expression computes an answer for the caller. It does not automatically assign that answer back into the process record.

Change it to return myproc()->pid + 1000;. When compiled, this kernel will read the PID, add 1000, and return the sum. The user program prints that sum. The evidence panel independently reads the process record at system-call entry and at process exit.

The dispatcher puts the handler’s returned value in the saved user a0 register, as shown below. The kernel keeps the user registers in a saved record called a trapframe while it handles the call. Setting its a0 field delivers the answer as the calling C function’s result.

C reminder: pointers and the -> operator

For a pointer p to a struct, p->pid means (*p).pid: follow the pointer, then read its pid member. Use the dot operator with a struct value itself. Reading a member and assigning to it are different operations.

p->pid        // read a member through a pointer
p->pid = 7;   // assign a new member value

What this shows

        
Changing an interface’s answer and changing the underlying state are different operations. return pid + 1000 changes the answer; assigning to pid would change state.

        

          A question to carry forward
          
If you changed the stored pid itself, would you still expect the kernel PID at process exit to match the value at syscall entry?
