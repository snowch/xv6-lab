Lock order prevents circular wait

Recognize a self-cycle and extend the reasoning to multiple locks.

If one execution path holds A and waits for B while another holds B and waits for A, neither can proceed. A consistent global acquisition order rules out that circular wait. Choosing an order requires inspecting every path that can hold the locks together.

The starter follows left then right and releases in reverse order. Trying to acquire left twice would make the running kernel code wait for itself. xv6 catches that case with panic: acquire rather than spinning forever.

A self-cycle is the simplest example, not a demonstration of multicore contention. The pinned wait implementation below explains a more subtle ordering constraint: it already holds the parent’s lock and must check the parent relationship before locking a candidate that might be an ancestor. Lock ordering is a property of the whole protocol.

C reminder: addresses passed to functions

&status gives the address of the caller’s variable, so a function can write a result there. The function’s return value is a separate result. A zero used as a pointer argument is a null pointer; wait(0) supplies no status address.

int status = 0;
int pid = wait(&status);
