Locks order the publication of protected state

Connect payload visibility to the ordering inside acquire and release.

Mutual exclusion is only part of the lock contract. Other CPUs must also observe the protected writes in the required order. The fences and atomic operations in xv6 prevent protected accesses from moving across the lock boundaries.

This probe publishes a payload and a ready condition under one real lock, then reads both under that same lock. The probe prints the payload read under the lock. Both the flag and the payload follow the protocol. Reading a flag without the shared synchronization would require a separate, carefully defined memory-ordering protocol.

This one-hart sequential experiment makes the protected data flow visible. Its successful output cannot prove weak-memory behavior on multiple CPUs. The ordering guarantee comes from the actual acquire/release implementation and its fences, which the source below shows.

C reminder: static state shared by callbacks

A file-scope static variable has one storage location for this compiled kernel unit and starts at zero. Its value persists between function calls in this VM, so a probe can arm an interrupt observer and later disarm it. An ordinary local variable is separate for each call. A fresh VM resets this state independently of the source draft saved in your browser.

static int watching;
watching = !watching;  // toggle between 0 and 1
