The kernel checks user pointers

Distinguish a checked syscall copy from a direct invalid user load.

A system call can receive a pointer without directly trusting it as a kernel address. xv6’s copy helpers translate user addresses through the calling process’s page table and reject an unmapped address.

The example asks the console to write four bytes from a deliberately unmapped user address. It does not dereference that pointer in user code. The kernel’s copy fails before it obtains a byte.

For this pinned xv6 console, consolewrite stops at that failed copy and returns the number of bytes sent: 0. The caller remains alive. Other operations can report failure differently, so read the actual path rather than assuming a universal return value.

C reminder: a pointer argument versus a dereference

Casting an integer to a pointer creates an address value; dereferencing it would request access to memory. Passing that value as an argument lets the called interface inspect it. The syscall’s result is determined by xv6’s checked-copy path, which this lesson explains.

write(1, (char*)0x40000000, 4);
// This call passes a pointer; it does not load *pointer in user C.
